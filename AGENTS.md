# AGENTS.md

## Repo layout

- Collection of Camunda Modeler plugins. Each plugin is a standalone npm package; there is no root `package.json`, workspace config, or CI.
- Only plugin today: `bpmn-sorter-plugin/`. Run all npm/node commands from that directory, not the repo root.
- `bpmn-sorter-plugin/dist/` is gitignored and generated by webpack; never hand-edit it. `bpmn-sorter-plugin/index.js` is the Camunda Modeler host entry and loads `./dist/client.bundle.js`.

## Commands (from `bpmn-sorter-plugin/`)

- `npm install`
- `npm test` — all tests via Vitest
- `npx vitest run test/xmlSorter.test.js -t "should sort props"` — single test
- `npm run bundle` / `npm run bundle:watch` — rebuild `dist/`; required after changing `client/` for manual installs
- `npm run format` — Prettier over `**/*.js`; there is no lint or typecheck step

## How the plugin works

- `client/client.js` registers `XMLSorterPlugin` as a bpmn-js plugin via `camunda-modeler-plugin-helpers`.
- `client/XMLSorterPlugin.js` listens to bpmn-js `saveXML.serialized` and returns `sortXml(event.xml)`; that returned string is what Camunda Modeler saves. It fails open: any error is logged via `console.warn` and `undefined` is returned, so the unsorted XML is saved. It also logs `findIntegrityIssues` (duplicate ids, dangling `bpmnElement`/`sourceRef`/`targetRef`) as warnings, never blocking.
- On/off state is owned by `menu.js` (Electron main process): `<userData>/bpmn-xml-sorter-plugin.json`, default on. The single menu entry's label shows the state (`Sorting on Save: ON/OFF`). `menu.js` emits `menu:action` `toggle-bpmn-xml-sorting` with `{ enabled }` on every menu rebuild while a BPMN tab is active (and on click, plus `menu:update`); the Modeler forwards it to the active tab's bpmn-js `editorActions`, where the plugin registered it and caches the value in `localStorage` (`bpmn-xml-sorter.enabled`). Menu entry is enabled only for `activeTab.type` `bpmn`/`cloud-bpmn`.
- `client/xmlSorter.js` holds the tested logic: recursive sibling sort by tag name, then `isExecutable` elements first among same tags, then `id`/body. Non-element nodes (whitespace text) keep their original slots; equal elements keep their original order.
- Sorting works on a parsed DOM tree. Keep it that way so namespace declarations survive; don't replace it with regex/string sorting.

## Gotchas

- `@xmldom/xmldom` 0.9 rejects unbound namespace prefixes, so every test fixture using `bpmn:`, `camunda:`, etc. must declare that namespace.
- Tests mostly compare with `normalizeXml` (whitespace-insensitive), but a few assert exact serialized strings where self-closing tags are normalized to ` />`. Match that format when adding fixtures.
- `sortXml` adds no indentation; it only sorts and normalizes `/>` to ` />`.
- `scripts/link.cjs` and `scripts/install.cjs` write to the user's real Camunda Modeler plugin directory (`~/Library/Application Support/camunda-modeler/...` on macOS). Don't run `npm run link` or `npm run install-plugin` unless asked; they mutate state outside the repo.
- Dependency upgrades use `ncu -u && npm install` (documented in the root README), not manual edits.
